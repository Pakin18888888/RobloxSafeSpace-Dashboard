01หน้า Login ที่เสนอเพิ่ม

โครงสร้างการเข้าถึง

เจ้าหน้าที่เข้าสู่ระบบ → ตรวจสิทธิ์ → เปิดเฉพาะหน้าที่ได้รับอนุญาต

การจัดลำดับนี้เป็นข้อเสนอ
Login / Session
→
ตรวจสิทธิ์
→
Dashboard

มีสิทธิ์ Overview ให้เปิด Overview · ไม่มีสิทธิ์ ให้เปิดหน้าที่อนุญาต · ไม่มีสิทธิ์ใดเลย ให้แสดงหน้าปฏิเสธการเข้าถึง

ขอบเขตของหลักฐานคลิปแสดงหน้าจอหลัง Login และชื่อ API แต่ไม่ได้สาธิตหน้า Login หรือผลการบันทึกข้อมูล จึงแยก “สิ่งที่เห็น” ออกจาก “พฤติกรรมที่เสนอ” ตลอดทั้งแบบนี้ ตัวเลขในต้นแบบเป็นข้อมูลสมมติ

สิ่งที่ Frontend ส่งต่อได้

  • โครงสร้างหน้าและเส้นทางใช้งาน 8 เมนู
  • สถานะ Login, loading, empty, error และไม่มีสิทธิ์
  • แบบฟอร์มและการยืนยันก่อนเปลี่ยนข้อมูล
  • รายการ API / ข้อสงสัยที่ทีมใช้ตกลงร่วมกัน

สิ่งที่ต้องยืนยันกับ Backend

  • Session, logout และรหัสผ่านชั่วคราว
  • ชื่อ permission และข้อมูลที่แต่ละสิทธิ์เห็นได้
  • Request / response / error ของแต่ละ API
  • ผลการส่งข้อความเข้าเกม และผลของ reset / delete
02 / USER FLOW

เจ้าหน้าที่ไปถึงงานที่ต้องการอย่างไร

เลือกเส้นทาง แล้วคลิกแต่ละขั้นเพื่ออ่านเงื่อนไขและหลักฐาน ลูกศรแสดงลำดับที่เสนอสำหรับ Frontend

ที่มาของข้อมูลเห็นในคลิปเสนอ Frontendต้องยืนยันกรอบเส้นประ = จุดตัดสินใจ
03 / SYSTEM WORKFLOW

ใครทำอะไร และส่งต่อข้อมูลตรงไหน

อ่านจากบนลงล่างตามหมายเลข ภายในแต่ละแถวอ่านจากผู้เริ่ม → ผู้รับงาน แบบนี้อธิบายการเชื่อมต่อที่เสนอ ไม่ใช่หลักฐานว่า Backend ทำครบแล้ว

Frontend รับผิดชอบ

ตรวจฟอร์ม แสดงสถานะ ปิดปุ่มระหว่างส่งคำขอ แสดงเมนูตามสิทธิ์ เคลียร์ข้อมูลเมื่อหมด session และแสดงสำเร็จเมื่อ Server ยืนยัน

Backend / Game รับผิดชอบ

ตรวจตัวตนและสิทธิ์ทุกคำขอ ตรวจข้อมูล บันทึก/อ่านข้อมูล จัดการ session และ audit รวมถึงการส่งข้อความและสถานะเกมตาม contract

04 / SCREEN INVENTORY

หน้าจอที่ต้องออกแบบ และสิทธิ์ที่เกี่ยวข้อง

Wireframe ย่อจัดวางใหม่เพื่อสื่อสารโครงสร้าง ใช้ชื่อเมนูเดิมในคลิป การแยกสิทธิ์ต้องถูกบังคับที่ Backend ด้วย

สิทธิ์ที่เห็นในหน้า Users 00:36–00:42

ในคลิปยืนยันได้เฉพาะ admin ที่มีทุกสิทธิ์ และแบบฟอร์มสร้าง role ใหม่ ส่วนชื่อ role อื่นและ permission keys ต้องให้ทีมกำหนด

หมวด สิทธิ์อ่าน สิทธิ์เปลี่ยนแปลง / เพิ่มเติม
จุดทบทวนสิทธิ์ข้อมูลขอความช่วยเหลือคลิปมี Alerts ในหน้า Players และข้อความว่า team note ทุกคนบน dashboard เห็น ขณะที่ proposal หน้า 32 เสนอให้จำกัดคำขอช่วยเหลือเฉพาะผู้รับเรื่อง จึงต้องยืนยันทั้งหน้าจอ API export และ logs ก่อนเชื่อมข้อมูลจริง
05 / CLICKABLE LOGIN CONCEPT

ลองเส้นทาง Login ก่อนเริ่มพัฒนาจริง

ข้อเสนอ Frontend · ไม่ใช่ระบบเข้าสู่ระบบจริง · ไม่ส่งข้อมูลไป Server และไม่เก็บรหัสผ่าน

ใช้ชื่อผู้ใช้ demo และรหัสผ่าน demo-only เท่านั้น · ผลลัพธ์ขึ้นอยู่กับสถานการณ์ที่เลือก · ไม่ใช้นโยบายรหัสผ่านนี้ในระบบจริง

สิ่งที่แบบนี้เสนอเพิ่มบังคับเปลี่ยนรหัสผ่านชั่วคราวก่อนเข้าข้อมูล ใช้ข้อความผิดพลาดทั่วไป และแยก 401 / 403 / network error ในการออกแบบ การแมปกับสถานะจริงต้องยืนยันจาก Backend
